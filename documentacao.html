1. Game Loop & Fixed Time Step

Em Ecos do Andarilho, a precisão rítmica exige que o motor não dependa da taxa de atualização do monitor do utilizador (FPS). Para evitar a dessincronização entre o áudio e a física em ecrãs de 60Hz vs 144Hz, implementámos um Fixed Time Step Accumulator acoplado ao requestAnimationFrame.

!

A Problemática do DeltaTime Simples
Multiplicar a gravidade apenas pelo DeltaTime (dt) causa erros de integração não-determinística. Um jogador a 30fps teria alturas de salto microscopicamente diferentes de um jogador a 144fps, arruinando os Ecos (eventos rítmicos).

core/engine_loop.js
const FIXED_TIME_STEP = 1.0 / 60.0; // 60 atualizações físicas por segundo garantidas let accumulator = 0.0; let lastTime = performance.now(); function gameLoop(currentTime) { let frameTime = (currentTime - lastTime) / 1000.0; if (frameTime > 0.25) frameTime = 0.25; // Prevenção de "Spiral of Death" lastTime = currentTime; accumulator += frameTime; // A Física roda num compasso de tempo fixo while (accumulator >= FIXED_TIME_STEP) { updatePhysics(FIXED_TIME_STEP); evaluateRhythmEvents(); // Avalia DSP e Inputs Buffers accumulator -= FIXED_TIME_STEP; } // A renderização interpola o tempo restante (smoothness visual) const alpha = accumulator / FIXED_TIME_STEP; renderScene(alpha); requestAnimationFrame(gameLoop); }

2. Pipeline de Renderização (WebGL 2)

O C3Runtime (motor interno do Construct 3) empacota automaticamente todas as texturas em Sprite Atlases de 2048x2048 em tempo de compilação. Para desenhar florestas e ruínas massivas sem sobrecarregar a Thread principal do browser, exploramos renderização em lote (Batching).

Draw Calls Instanciadas

Em vez de invocar a GPU para desenhar cada Tile de relva individualmente, o sistema utiliza gl.drawElementsInstanced. Centenas de Tiles estáticos são enviados para a GPU numa única chamada, baixando as Draw Calls médias de ~800 para menos de 15 por frame.

OffscreenCanvas & Workers

O processamento estrutural do jogo roda num Web Worker isolado. A renderização é enviada de forma assíncrona via interface OffscreenCanvas, libertando a Main UI Thread para captar eventos de ecrã tátil com 0ms de bloqueio.

3. Processamento Digital de Sinal (DSP)

Para ler os "Ecos", não dependemos apenas de contadores matemáticos fixos (BPM estático). A arquitetura utiliza a WebAudio API para acoplar um AnalyserNode ao buffer da música BGM. É aplicada uma Análise Rápida de Fourier (FFT) para detetar picos de energia nas baixas frequências (Kick/Bass).

audio/beat_detector.js
const audioCtx = new (window.AudioContext || window.webkitAudioContext)(); const analyser = audioCtx.createAnalyser(); analyser.fftSize = 256; const bufferLength = analyser.frequencyBinCount; const dataArray = new Uint8Array(bufferLength); function detectEcoBeat() { analyser.getByteFrequencyData(dataArray); // Isolar frequências graves (Kicks e Bass ~ 20Hz a 100Hz) let bassEnergy = 0; for (let i = 0; i < 5; i++) { bassEnergy += dataArray[i]; } bassEnergy /= 5.0; // Se a energia ultrapassar o limiar, um "Eco" Global é ativado no mapa if (bassEnergy > ENERGY_THRESHOLD && !isBeatActive) { triggerGlobalEchoState(); } }

4. Física e Spatial Partitioning

A deteção de colisão tradicional iterando sobre todos os objetos (O(n²)) destruiria a bateria e a performance em dispositivos móveis. Em vez disso, o mundo de Ecos do Andarilho é indexado utilizando um algoritmo de particionamento espacial.

  • Grelha Espacial (Spatial Hash Grid): O mapa de jogo é dividido num tabuleiro invisível. Quando o Andarilho se move, a engine só calcula cruzamentos de Bounding Boxes (AABB) com plataformas e inimigos que residam exatamente na mesma célula da grelha que o herói, convertendo a carga de CPU para perto de O(1).
  • Continuous Collision Detection (CCD): Para evitar que o personagem "atravesse" o chão se estiver a cair demasiado rápido (Tunneling), a engine calcula o vetor de Sweep em vez do passo estático.

5. Otimização da V8 Engine (Pooling)

Nos motores JavaScript (como o V8 no Chrome), instanciar milhares de partículas (Ex: faíscas ao efetuar um salto "Eco Perfect") com o comando new Object() e destrui-las força o Garbage Collector (GC) a limpar a RAM. Se o GC iniciar a meio de uma batida musical, o jogo sofre um micro-stutter (engasgo).

i

Object Pooling Pré-Alocado
A arquitetura anula este problema gerando 100 instâncias inativas de partículas durante o Loading Screen. Estas são armazenadas num vetor contíguo. Quando o jogador salta, o código simplesmente pega numa instância adormecida, altera as suas coordenadas x,y, e torna-a visível. O GC nunca precisa de ser ativado durante a gameplay ativa.

6. Serialização & Save States

Para persistir o progresso do jogador de forma segura num ambiente Web *stateless*, não utilizamos o localStorage padrão devido às suas limitações síncronas que bloqueiam a Thread. Optámos pela base de dados assíncrona nativa do browser.

TecnologiaProcesso de Serialização (Save System)
IndexedDB APIA gravação do progresso (Níveis Desbloqueados, Moedas, Herói) ocorre de forma não-bloqueante no disco do browser, garantindo que o jogo não sofre quebras ao fazer Auto-Save após um checkpoint.
LZString Base64O JSON que contém as variáveis de jogo é comprimido via algoritmo LZ-based antes de ser armazenado, mitigando a adulteração acidental e reduzindo a pegada no disco do cliente.

7. Infraestrutura Edge (CI/CD Vercel)

O ciclo de vida do software segue as diretrizes DevOps. O repositório está integrado nativamente com a CDN global da Vercel para entregas contínuas (Continuous Deployment). Os binários WebAssembly (WASM) e ficheiros WebP do jogo são fortemente cacheados nas Edge Networks geográficas.
